# AI rule statistics and operator image lookahead

Local implementation, 2026-09-16. No production queries, push, deployment, or merge.

## SQL changes

The rules endpoint still calculates exact counts in one aggregate query within the existing
five-second read-only, repeatable-read transaction.

- PENDING and the oldest 100 recoverable PROCESSING tasks are separate, disjoint UNION ALL branches.
- The ordered first-match CASE and the claim's shared availability/rule predicates are retained.
- Image availability is still checked against image_asset, including cloud keys and retention.
  The equivalent predicate (local OR key-present) AND (local OR recent) enables its partial index.
- Historical Processing/Completed/Failed ownership still comes from issued_rule_id.
- Statistics join SHA-256 hex image IDs with COLLATE "C". These are identifiers generated by ImageId,
  so bytewise equality avoids locale comparisons without changing task ordering or database column collations.

Three indexes were necessary on the measured fixture: a status aggregation index, a covering index for
PENDING candidates ordered by image ID, and a covering index for authoritative image availability.
The first two changes alone occasionally still exceeded five seconds. The final indexes avoid scanning
large metadata/result heap rows, sorting candidate IDs, and expensive locale comparisons.

Remaining can include an expired PROCESSING task in the bounded recovery preview while Processing
still counts its current persisted status. The four columns are not a disjoint total; this is unchanged.

## Index migration

Run only when the target database change is authorized:

    psql <connection> -f scripts/ai-rule-statistics-index.sql

Use psql outside a transaction; do not use --single-transaction. The focused script performs no backfill
or task updates. It builds indexes CONCURRENTLY, uses a three-second lock wait limit, validates existing
index definitions/collation, and rebuilds its own invalid indexes after an interrupted build.
A conflicting definition fails for inspection instead of silently accepting an unrelated index.
It shares the existing AI migration advisory lock and restores the caller's timeout settings.

The full ai-pull-integration.sql includes this script for initial installations. Existing installations
should run only the focused script for this change. Index creation still consumes I/O, CPU, and disk space.
The application does not create these indexes on startup.

## Reproducing the SQL benchmark

Use a disposable PostgreSQL 17 database named rv_ai_stats_analysis, with test credentials
validator/validator. The controlled container used 2 CPU, 4 GiB RAM, 512 MiB shared_buffers,
16 MiB work_mem, and 512 MiB /dev/shm. Never point the fixture at an application database.

Initialize an empty schema once with this application's Hibernate schema generation, explicitly
pointing its datasource at that disposable database and disabling B2, Slack, watching, and cleanup.
Stop the application before loading the fixture.

    psql <test connection> -f src/test/sql/ai-rule-statistics-scale-fixture.sql
    mvn -Dtest=AiRuleStatisticsLargeScaleTest -Dai.rules.scale.url=jdbc:postgresql://127.0.0.1:55440/rv_ai_stats_analysis test

The fixture contains 5,000,000 images and 4,400,000 AI tasks:
440,000 PENDING, 44,000 PROCESSING, 3,872,000 COMPLETED, and 44,000 FAILED.
It includes two game codes, overlapping/default rules, expired leases, cloud retention, and obsolete rule IDs.
It omits unrelated secondary image indexes during bulk loading; primary/unique keys and the relevant
AI/availability indexes remain. Results describe this synthetic distribution, not a production guarantee.
Freshly vacuumed pages also differ from a production database with ongoing writes and bloat.
Fixture IDs are sequential, padded ASCII identifiers rather than randomly distributed SHA-256 values.

The opt-in test invokes the actual AiTaskRepository, asserts the frozen old query times out at five seconds,
compares every count with the old result, and runs the new query three times with two parallel workers and
three times without them. Only diagnostic EXPLAIN runs use a longer limit; the tested query and application
retain five seconds. Plans are written to target/ai-rule-statistics-scale/old-plan.txt and new-plan.txt.
Without ai.rules.scale.url this large fixture test is skipped; regular correctness/100k scale tests still run.

Full verification, including the large fixture:

    mvn clean verify -Dai.rules.scale.url=jdbc:postgresql://127.0.0.1:55440/rv_ai_stats_analysis
    node --test src/test/js/*.test.cjs

## Recorded verification results

Final run: PostgreSQL 17.11, 2026-09-16. The old query was cancelled at the unchanged five-second
limit; a separate diagnostic execution completed in 10,325 ms. The old SQL was tested with the new
indexes already present, so these results also show that adding indexes alone did not fix its join.

| Measurement | Old SQL | New SQL |
| --- | ---: | ---: |
| EXPLAIN execution time | 10,325 ms | 1,441 ms |
| Shared blocks hit / read | 213 / 508,084 | 55,867 / 12,079 |
| Temporary blocks read / written | 48,608 / 48,608 | 0 / 0 |
| Actual repository calls, two workers allowed | exceeds 5 s | 3,849 / 728 / 712 ms |
| Actual repository calls, parallel workers disabled | not measured | 1,229 / 995 / 1,048 ms |

The first new repository call is reported separately from the faster repeated calls; caches were not
flushed between calls. EXPLAIN adds instrumentation overhead. The recorded old plan allowed two
workers; the recorded new plan had them disabled. These are local fixture results, not a latency SLA.

The important plan change is from full heap scans and a 16-batch hash join to index-only scans and
a merge join for PENDING, with a bounded nested-loop lookup for 100 recoverable tasks. All three
main index-only scans had zero heap fetches in the recorded new plan. Exact counts matched the old
query for every returned rule and status; Remaining was 2,934 / 261,134 / 132,032.

Index sizes on this fixture: issued-rule/status 27 MB, PENDING candidates 66 MB, image availability
502 MB (595 MB total). All are valid and ready. Re-running the migration kept existing valid indexes;
an interrupted concurrent build was recovered on the disposable database, and an unexpected index
definition was rejected.

- Full `mvn clean verify` including the large fixture: 429 tests, zero failures/errors/skips.
- JavaScript suite: 88 tests, zero failures/skips.
- Browser fixture: all 15 scenarios passed, with no page JavaScript errors.
- No production queries, application database changes, push, deployment, or merge were performed.

## Operator lookahead

Claim and decision responses add nullable nextImageId and nextImageUrl alongside item.
The hint comes from the existing, unexpired candidate buffer for the selected filters.
Reading it does not refill the buffer, perform another SQL search/count, remove a candidate,
assign a task, or extend a lease. There is still one active assignment per operator.

The browser preloads at most one image after the current image is ready. On a matching actual ID
it adopts the same Image element, including an in-flight request, and waits for decoding before enabling
decisions. On a mismatch it discards the hint and loads the actual task normally.
No blob/object URLs, new dependencies, cache-policy changes, or authentication changes are introduced.

A different operator may claim the hinted image first. Hints may also be absent at buffer expiry or
when batching is disabled. A cache miss affects speed only; the existing database claim rechecks eligibility.

Filters, task errors, empty results, logout, pagehide, and hiding the tab clear the preload.
Late responses/image events are guarded by request/image versions. A filter change during a decision
waits for that mutation to finish before replacing its assignment.
Retry delays, availability checks, zoom/pan, and keyboard decision gating remain in place.

## Browser regression fixture

    node src/test/browser/review-preload-server.cjs

Run src/test/browser/review-preload.js using the Playwright browser tool's filename argument.
It opens isolated contexts against localhost:18992/18993 and closes them after each case.
The fixture serves the real review template, CSS and review JavaScript. Only the API/image responses
and unrelated date-picker initialization are controlled test doubles; no application data is used.

Cases cover matching/no-second-download, 307 cross-origin/no-CORS/no-store, in-flight adoption,
mismatch, preload failure, filtering and stale events, a pending decision/filter race, retry,
availability recovery/hold, decision failure, expired authentication, empty queue, logout, pagehide,
and hidden-tab cleanup. Actual B2 credentials/network were not used.
